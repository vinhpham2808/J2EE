1 Mục tiêu

Mục tiêu của phương án này là đưa dự án lên môi trường thật để có thể dùng demo một cách nghiêm túc, ổn định và dễ mở rộng về sau.

  • Website chạy bằng domain thật botdevgroup.me
  • Backend API chạy bằng domain thật api.botdevgroup.me
  • Ứng dụng mobile gọi đúng API production
  • Có lớp chống spam và DDoS cơ bản
  • Có hệ thống cảnh báo tự động khi có sự cố (qua Amazon SNS)
  • Đủ ổn định để demo cho người khác xem một cách nghiêm túc

2 Kiến trúc tổng thể

Luồng truy cập chính:

  • Người dùng web/mobile → Cloudflare
  • botdevgroup.me → Cloudflare → S3 (Static Web Hosting)
  • api.botdevgroup.me → Cloudflare → ALB → EC2 Auto Scaling Group
  • Backend trên EC2 kết nối tới Aurora MySQL, RDS Proxy, Redis, DynamoDB, SQS, S3, CloudWatch và SNS

2.1 Lớp mạng bắt buộc: VPC, subnet, security group

Để triển khai production nghiêm túc trên AWS, không chỉ có các dịch vụ như EC2, ALB, Aurora hay Redis, mà còn phải thiết kế lớp mạng chuẩn. Vì vậy phương án này bắt buộc có VPC.

Bố cục mạng khuyến dùng:

  • 1 VPC
  • 2 Availability Zones
  • 2 public subnets
  • 2 private app subnets
  • 2 private data subnets

Bố cục subnet nên dùng

Loại subnet Mục đích Dịch vụ nên đặt
Public Subnet A/B Nhận traffic từ internet ALB, NAT Gateway
Private App Subnet A/B Chạy logic ứng dụng EC2 web-api, EC2 worker
Private Data Subnet A/B Chứa dữ liệu nội bộ Aurora MySQL, ElastiCache Redis

Luồng mạng chuẩn

  • Cloudflare → ALB: ALB phải public nên đặt ở public subnets
  • ALB → EC2 web-api: EC2 nên đặt ở private app subnets
  • EC2 → Aurora / Redis: database và cache nên đặt ở private data subnets
  • EC2 → S3 / CloudWatch / SNS / Secrets Manager / API ngoài: outbound qua NAT Gateway hoặc VPC Endpoints

Security Group nên chia

Security Group Inbound Outbound
sg-alb 443 từ internet hoặc từ Cloudflare IP ranges Tới sg-app
sg-app Chỉ từ sg-alb Tới DB, Redis, NAT, API ngoài, SNS endpoint
sg-db Chỉ từ sg-app Giới hạn nội bộ
sg-redis Chỉ từ sg-app Giới hạn nội bộ

Có cần bastion host không?

Khuyến nghị không cần bastion host. Nên dùng AWS Systems Manager Session Manager để truy cập EC2. Cách này an toàn hơn vì không phải mở cổng SSH 22 ra internet.

Có cần NAT Gateway không?

Có, nếu EC2 private cần truy cập internet outbound để:

  • Gọi API bên thứ ba như Gemini, OpenRouter, Brevo, PayOS
  • Gọi SNS endpoint khi publish từ backend
  • Lấy secrets / gửi logs / gọi S3 nếu chưa dùng endpoint

Nếu muốn tối ưu chi phí, có thể bổ sung VPC Endpoints cho các dịch vụ AWS hay dùng nhiều nhất: S3, Secrets Manager, CloudWatch Logs, SNS.

3 Các dịch vụ sẽ sử dụng

🛡️ Cloudflare

  • DNS
  • Proxy
  • DDoS Protection
  • WAF
  • Rate Limiting
  • Turnstile

  • EC2 Auto Scaling Group: chạy Spring Boot

  • Aurora MySQL: database chính
  • RDS Proxy: giảm áp lực connection
  • ElastiCache Redis: cache, rate limit
  • Amazon DynamoDB: lịch sử chat

🔧 Vận hành (AWS)

  • SQS + DLQ: queue async jobs
  • EventBridge Scheduler: job định kỳ
  • Amazon S3: lưu trữ báo cáo & hóa đơn
  • Secrets Manager: quản lý secrets
  • CloudWatch: logs, metrics, alarms
  • Systems Manager: quản trị EC2

🔔 Cảnh báo (AWS)

  • Amazon SNS: gửi cảnh báo qua email, SMS khi alarm kích hoạt
  • Nhận trigger từ CloudWatch Alarms

5 Cấu hình mobile production

Ứng dụng mobile hiện đọc API URL từ biến môi trường. Khi build bản production, phải dùng domain thật, không dùng IP LAN.

Giá trị cần dùng khi build production:

EXPO_PUBLIC_API_BASE_URL=https://api.botdevgroup.me/api/v1.0

  • IP như 192.168.x.x chỉ dùng để test nội bộ
  • Khi đổi API domain thì phải build lại APK/AAB
  • Mobile app của dự án đang dùng Bearer token, nên chỉ cần API domain public là đủ

6 Vì sao chọn EC2 thay vì ECS/Fargate

  • Dễ hiểu hơn với mô hình máy chủ truyền thống
  • Dễ quản trị nếu nhóm quen làm với server
  • Vẫn scale được nhờ Auto Scaling Group
  • Vẫn kết hợp tốt với ALB, CloudWatch, Secrets Manager, RDS Proxy và Cloudflare

7 Cách chia backend trên EC2

Không nên dồn mọi thứ vào một EC2 duy nhất nếu muốn demo nghiêm túc.

Thành phần Mục đích Khuyến nghị

8 Chống spam và DDoS

Lớp 1: Cloudflare

  • Bật proxy cho botdevgroup.me và api.botdevgroup.me
  • Bật WAF và DDoS protection
  • Đặt rate limit cho các endpoint nhạy cảm
  • Dùng Turnstile cho đăng ký, quên mật khẩu, resend OTP, email report nếu cần

Endpoint cần bảo vệ đặc biệt

  • /api/v1.0/login
  • /api/v1.0/register
  • /api/v1.0/forgot-password
  • /api/v1.0/otp/resend
  • /api/v1.0/email/*
  • /api/v1.0/ai/*
  • /api/v1.0/payments/payos/create

Lớp 2: Backend

  • Rate limit nên dùng Redis, không dùng in-memory
  • Đọc IP thật từ CF-Connecting-IP
  • Tách email/report sang queue để tránh block request

9 Những điểm cần sửa trong code trước khi demo nghiêm túc

  • Bỏ rate limit in-memory, chuyển sang Redis-based rate limit
  • Bỏ phụ thuộc request.getRemoteAddr() để xác định IP thật
  • Chuyển email/report sang mô hình async qua SQS + worker
  • Chuyển scheduled jobs sang EventBridge Scheduler
  • Tắt ddl-auto=update trong production và dùng migration chuẩn
  • Bỏ AWS access key/secret key tĩnh, chuyển sang IAM role + Secrets Manager
  • Bỏ logic clear toàn bộ Redis cache lúc startup
  • Bỏ AWS Lambda, tự sinh báo cáo Excel (Apache POI) và hóa đơn HTML trên Backend, upload trực tiếp lên S3
  • Lưu hình ảnh/hóa đơn import lên S3, trả về URL công khai và lưu vào DB khi confirm

10.2 Cách giải thích ngắn gọn cho bạn bè không rành AWS

Nói ngắn gọn dễ hiểu:

  • Cloudflare là lớp đứng ngoài cùng để bảo vệ domain, chống tấn công, điều hướng truy cập và cache các file tĩnh.
  • Frontend web là các file tĩnh được lưu trữ trực tiếp trên Amazon S3 và phân phối thẳng qua Cloudflare.
  • Backend API chạy trên nhiều máy EC2 phía sau ALB để có thể scale và chia tải.
  • Dữ liệu chính lưu ở Aurora MySQL; Redis dùng để cache và rate limit; DynamoDB dùng cho lịch sử chat.
  • Những việc nặng như email/report đưa qua queue để hệ thống không bị chậm.
  • Báo cáo & Hóa đơn được xử lý trực tiếp trên Backend và lưu trữ vào S3.
  • Hình ảnh hóa đơn khi người dùng import sẽ được tự động tải lên S3 và được tham chiếu qua URL trên S3.
  • SNS là "hệ thống còi báo động" — khi máy chủ có vấn đề, SNS tự gửi email/SMS để team xử lý ngay.
  • Mobile app khi build bản phát hành sẽ gọi thẳng vào https://api.botdevgroup.me/api/v1.0.
